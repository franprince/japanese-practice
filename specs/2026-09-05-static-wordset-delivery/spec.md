# Static wordset delivery

Continued under the user's instruction to implement the next backlog item and open a PR.
Base: `develop` at `e40e0fd`; backlog PR 2 merged as #57.

## Problem and goals

The wordset route reads and parses large JSON files even for version checks.
Publish a small static manifest and immutable content-addressed payloads during
build. Clients use the manifest for update checks and consent sizes, and download
payloads directly. Remove the dynamic wordset route. Preserve word selection,
IndexedDB transactions, consent, cancellation, retries, and failure semantics.

## Contract

`/wordsets/manifest.json` has `schemaVersion: 1` and `datasets.en` / `datasets.es`.
Each entry has `language`, positive integer `version`, positive integer `bytes`,
SHA-256 `checksum` (64 lowercase hex digits), and `url` matching
`/wordsets/<language>-<checksum>.json`. Bytes and checksum describe the exact
uncompressed UTF-8 asset. Existing numeric dataset versions remain unchanged.
The manifest is revalidated (`Cache-Control: no-cache`); payloads are immutable
for one year. English and Japanese share the English entry.

Builds validate both source datasets, copy their exact bytes, and publish the
manifest after both assets exist. Identical inputs produce identical outputs;
any byte change changes the URL, including changes without a version bump.
Generated artifacts are ignored by Git and generated by dev/build and dataset
commands. Existing source JSON files remain the build inputs.

Clients validate manifest entries before following same-origin asset URLs.
Downloads verify shape, version, byte count and checksum before persistence.
Cache entries retain an optional delivery checksum for version comparison.
Legacy entries remain usable and undergo one background refresh/offer to acquire
that checksum. A current checksum avoids payload transfer on repeat visits.
Mobile update checks fetch only the manifest and preserve explicit consent.
Browser HTTP caching handles conditional manifest requests and 304 responses;
a raw 304 without a browser-provided cached body is an explicit protocol error.
Manifest/asset failures preserve ready cached data and use existing typed errors.

## Acceptance and tests

- No request handler parses a complete wordset; no active client uses the old route.
- Outputs are deterministic, complete for EN/ES and have matching hashes/sizes.
- Invalid manifests, missing assets, bad hashes/versions and interrupted downloads fail explicitly.
- Current cache checks transfer only metadata; changed content selects a new URL.
- Mobile size comes from metadata without downloading a payload before consent.
- Existing lifecycle tests, focused transport/build tests and EN/ES browser smoke tests pass.
- Typecheck, lint, unit tests and build pass; production HTTP checks verify cache headers and conditional manifest requests.
